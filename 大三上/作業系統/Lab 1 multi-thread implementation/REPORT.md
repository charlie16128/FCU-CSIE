# 多執行緒賽馬程式討論

## 使用多執行緒與不使用多執行緒的程式流程有何差別？

### 不使用多執行緒

若程式只有一條執行流程，所有馬匹必須輪流更新。例如主迴圈先移動 1 號馬，再移動 2 號馬，直到最後一匹，接著才進入下一輪。這種流程的執行順序固定、容易理解，也不需要處理多條執行緒同時修改排名的問題，因此除錯與測試較簡單。

但是，若直接在 Swing 的 Event Dispatch Thread（EDT）中執行包含迴圈與 `sleep` 的整場比賽，EDT 就無法及時處理重繪、按鈕和視窗事件，GUI 會看起來凍結。非多執行緒版本若要保持流暢，通常必須改用 Swing `Timer`，在每一次計時事件中依序更新所有馬匹，讓每次工作都很短。這仍是單執行緒的合作式流程，而不是每匹馬獨立執行。

### 使用多執行緒

本程式讓每匹馬都有自己的 `Thread`。每匹馬可獨立休眠、計算經過時間、更新位置及消耗體力；作業系統的排程器會交錯執行這些執行緒。程式結構更接近「多匹馬同時前進」的模型，而且某匹馬等待時不會阻止其他馬繼續執行。

多執行緒也帶來非確定性：即使速度設定相同，實際排程順序仍可能不同。兩匹馬可能幾乎同時抵達終點，因此排名、首匹完賽事件與加速啟用都必須同步保護。本程式在 `RaceController` 的臨界區中更新完賽集合與排名，確保同一匹馬不會重複加入，也確保只有第一個完成的執行緒能觸發全場加速。

Swing 本身不是執行緒安全的，所以馬匹背景執行緒不能直接修改 JLabel、按鈕或面板。本程式讓背景執行緒只更新模型狀態，再由 Swing `Timer` 約每 33 毫秒取得不可變快照並重繪；排名與狀態訊息則透過 `SwingUtilities.invokeLater` 回到 EDT 更新。

## 比較

| 面向 | 單執行緒流程 | 多執行緒流程 |
|---|---|---|
| 執行方式 | 依固定順序輪流更新所有馬 | 每匹馬由獨立執行緒推進 |
| GUI 反應 | 長迴圈若放在 EDT 會凍結；需用 Timer 切成短步驟 | 背景工作不占住 EDT，GUI 可持續處理重繪與事件 |
| 結果順序 | 通常較可預測、容易重現 | 受到排程影響，完成順序具有非確定性 |
| 共享資料 | 通常不需要鎖 | 排名、完成集合與賽事狀態必須同步 |
| 程式複雜度 | 較低，除錯容易 | 較高，需處理競爭條件、可見性、中斷與關閉 |
| 適用情境 | 工作量小、固定順序、可用事件迴圈分步完成 | 多個可獨立進行或常等待的工作 |

## 多執行緒是否一定比較快？

不一定。這個賽馬程式的重點是展示獨立執行流程與 GUI 反應性，而不是大量 CPU 計算。建立及排程執行緒本身有成本，執行緒越多也會增加同步與切換負擔。如果所有工作都是很短的計算，單一 Swing `Timer` 可能更簡單且足夠流暢。

多執行緒較適合工作能彼此獨立、包含等待，或需要在背景進行而不能阻塞 UI 的情況。若工作大量使用 CPU，是否加速還取決於 CPU 核心數、任務能否真正平行化，以及同步成本。

## 結論

單執行緒的優點是流程清楚、結果容易預測且維護成本低；多執行緒的優點是能將獨立工作分開執行，避免其中一項工作阻塞整個應用程式。本作業採用「一匹馬一執行緒、控制器同步共享狀態、Swing EDT 專責畫面」的分工，能同時示範並行、同步、執行緒生命週期與 GUI 執行緒安全。
